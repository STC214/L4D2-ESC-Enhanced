**当前本机已验证“进入战役前选择新喷漆并实际喷绘”有效。** 字符串接口修复为 DLL 0.2.3 后，进一步把 80 个编号 VTF/VMT 放入 MOD 对应的 update 路径，用户确认新图案生效。局内更换不即时刷新，尚未实现强制会话刷新；不承诺任意服务器或新游戏版本通用。Go + Win32 管理工具现为 1.1.1，支持整目录导入与自然排序，见 [工具说明](喷漆导入工具.md)。本次与 C 一起纳入 [v1.4.0 汇总预发布](releases/v1.4.0.md)。以下各阶段失败／待验证描述按其写作阶段保留，不替代此处当前状态。

不读取或发布用户已有喷漆图像，不合并任何已有喷漆包，不改 C；发布素材仅为自制编号测试图。完整人工目录对话框、新图片观感及更多游戏场景仍待试用。

## 已得到的证据

- 本机 `bin/gameui.dll` SHA-256：`321ec9b5865582330af61e81eb347da31cc213cc6c95b80d6d98170b8a5fbb40`。
- 原生列表装载路径最多接收 16 项；不能只在清单中追加更多条目来扩容。
- 原生选择处理函数位于当前文件的 VA `0x1006a620`。它从页内索引读取路径，然后调用 `cl_logofile` 字符串设置及预览更新。地址依赖本机版本，不作为跨版本通用偏移。
- 在 Unicorn 中实际执行该函数的机器码，分别将独立目录的 40 项映射到每页最多 12 个模拟对象槽位；第 17、40 项及全部边界均到达预期的设置和预览参数。
- **CVar 服务、字符串辅助函数、预览绘制服务等依赖是模拟的**；模拟对象槽位由测试预填充。该重放本身没有实现真实游戏内分页绑定，未证明真实绘制、联网喷漆上传、设置持久化或页面交互成功。
- 根据该结果，可继续做独立目录分页，不必扩大原生固定数组。正式运行时桥接仍需验证；测试不修改游戏进程或磁盘 DLL。

## 阶段 2：分页界面与桥接原型 0.2.0

- 原型入口资源位于 **选项 → 多人游戏 → CSP TEST**，不是直接修改 C 的 ESC 入口。
- 4 页，每页最多 12 项（4×3），末页 4 项。点击编号进入对应大预览确认页；取消返回所在页，不应用。确认页的应用按钮发送专用命令。
- 专用命令严格限制为 `CSP_TEST_APPLY_001`～`040`；额外字符、未知编号等不作为控制台命令执行。当前版本只支持自制编号图，尚无自定义素材导入。
- 根据阶段 1 结果，桥接进一步简化：**不写原生槽位数组**，在原生 Multiplayer 命令入口仅截获专用应用命令，用 `IConVar::SetValue(const char*)` 设置并核对 `cl_logofile`。普通命令继续原处理；失败不进一步请求关闭多人设置页，成功后请求原生 `Back`。原生 Flyout 自身会在转发命令时先收起弹层，因此不保证失败时确认弹层保持打开。
- 只在游戏窗口线程上安装及执行桥接。GameUI、engine、vstdlib 按已检查文件 SHA-256 匹配；不匹配停止，不猜测偏移。不修改磁盘 DLL、CVar 标志、服务器规则或 C 的 DLL。运行期使用专用位置的临时跳转，原型 DLL 保留至进程退出，因此卸载前必须完全退出游戏。
- 原生选择器资源保留，新增入口只衔接两处上下导航；另外覆盖游戏原生 `multiplayer.res` 以添加入口。这可能和其他改同一路径的 UI MOD 冲突，尚未进行全部已安装 MOD 的冲突扫描。与 C 的包内资源没有功能路径重叠。
- 静态检查修复了早期网格导航闭环：现在键盘上下导航能从网格到达上一页、下一页和返回按钮。

## 0.2.3：应用字符串接口修复

用户报告 UI 正常但地图中没有喷绘。旧版实机日志对编号 039、011 均记录 `APPLY_READBACK_FAILED`，没有 `APPLY_VERIFIED`；因此先排查应用链路，不调整服务器、上传开关或贴花设置。

本机 engine 的 IConVar vtable `0x103ec550` 显示：槽 2 的 thunk `0x10283310` 转发浮点设置，槽 3 的 `0x10283300` 转发字符串设置。原型沿用了少一个 Color 重载的接口描述，MSVC 把字符串调用安排到槽 2。旧模拟测试也使用同一不准确声明，所以只验证了自洽，未发现真实 ABI 差异。

修复：用已经核对的显式 `__thiscall` 槽 3 调用，方法归属检查也改为槽 3；保留精确变量名、参数标志和实际字符串读回。日志现同时记录 requested／actual、setter_slot 和 flags_unchanged，失败不再只给笼统结果。

补充了两类交叉证据：四重载原生风格 C++ 接口模拟先复现旧调用误入浮点方法，再验证全部 40 个编号调用正确字符串方法；另外实际执行 engine 的两个 thunk 机器码，记录它们分别转发到浮点／字符串底层服务。底层服务仍是模拟，不把这两项写成游戏内已成功。

两轮完整复审通过，31 项 Python 测试及原生 ABI／窗口／命令测试通过；VPK 的 166 个功能成员不变，仅版本说明更新，独立 DLL 修复。已在游戏退出状态部署，安装文件及回退备份校验通过，C 未改。

## 0.2.3 实机复测：路径写入成功，实际喷绘仍为旧图案

用户确认预览正常，但地图里显示原有喷漆。实机日志记录编号 002、001 均为 `APPLY_VERIFIED`，`setter_slot=3`、requested 与 actual 完全相同，`flags_unchanged=1`。退出后的 `left4dead2/cfg/config.cfg` 也保存了 `materials/vgui/logos/csp_test/test_001.vtf`。因此不能再把本次问题归结为前一版的字符串 setter 调用失败；即时读回和退出配置也不支持“必然被旧菜单覆盖”的结论。

继续分析同一 SHA-256 的 engine.dll，发现设置路径之外还有独立的消费流程：

- `0x10091382` 读取 cl_logofile 的 parent/string，调用 `0x10090860`；后者进行文件存在性、512 KiB 上限、CRC 和缓存准备，失败时可能输出 `Couldn't find customization file '%s'.`。
- `0x1018fe6f` 读取 cl_logofile，在 `0x1018fea4` 指定 **MOD** 搜索路径，检查并打开选中的 VTF；读取成功后复制到固定名 `materials/vgui/logos/spray.vtf`，随后同样处理 VMT。此段属于 `0x1018fb70` 的配置保存流程，不是字符串 setter 本身。
- 本机 gameinfo.txt 注释说明 MOD 对应第一条 Game 搜索路径；当前第一条为 `update`。检查 `update` 与 `left4dead2` 的对应位置均没有自制编号的松散 VTF/VMT，也没有松散 spray.vtf/spray.vmt；自制素材当前只放在测试 VPK 内。

**结论边界**：已确认“路径成功”与“引擎实际喷绘成功”是两个验收项；当前实际喷绘尚未通过。优先验证 MOD 搜索路径可见性及固定 spray 资源／会话缓存，不再盲改 UI 或贴图亮度。尚未取得运行时 MOD 文件打开结果，因此 VPK 挂载范围与缓存原因仍是待验证假设，不宣称唯一根因已经实证。本次只读诊断未替换插件、VPK、游戏配置或 C。
